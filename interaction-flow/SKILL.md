# 交互闭环解读

把需求方案里的交互讲清楚：谁发起，谁接力，凭什么关联同一笔业务，什么时候完成，后续变化怎样继续处理。流程可以从 C 端、B 端、服务调用、事件、回调或定时任务开始，也可以全程没有人工操作。

## 调用与路径

- Codex：`$interaction-flow 根据这份需求方案梳理交互闭环，生成泳道图。`
- Claude Code：`/interaction-flow 根据这份需求方案梳理交互闭环，生成泳道图。`
- 两端均可通过自然语言提出同类请求。相对输入和输出路径按用户当前业务项目目录解析。
- 技能资源相对正在读取的本 `SKILL.md` 定位。执行脚本时先确定该文件的实际父目录，再使用其中的 `scripts/render_flow.py`；用户项目目录不需要存在同名脚本。

## 事实依据

- 以用户指定的需求方案及其原型、截图、补充说明为事实来源。同一目录中的其他文件只有确属本需求时才纳入，不默认合并整个 workspace。
- 先读完整材料，再梳理链路；有内嵌流程图或原型时查看原图，不能只提取文字。图文冲突保留双方出处，不擅自选一方覆盖另一方。
- 用户明确给出的澄清或评审结论按其适用范围沿用。已经确认通过的产物保留为本需求的评审参考，除非用户要求或材料发生变化，不重新改写；它不能代替新需求的方案。
- 历史测试方案、模型生成的解释和常见技术做法不自动成为事实。需求没写的网关、数据库、消息队列、重试、补偿和一致性保证，不补成确定流程。
- 已明确、分析假设、待确认分别标注。可以补充解释性推断，但不能用假设填出一条看似完整的确定链路。局部缺口就地标出，继续整理已有事实；影响主干或互相矛盾的问题汇总澄清。

## 梳理方式

### 1. 确定这条链路要完成什么

从用户目的确定起点、终点和主视图，再从材料选取相关事实。材料涉及多个入口或生命周期阶段，不代表这些内容都要展开；到达用户指定的完成点后停止延伸。

- 业务流程回答“谁做什么、经过什么判断、何时生效或结束”，用业务动作、条件和状态表达。
- 模块联动回答“哪些模块各管什么、如何依赖或接力”，用模块职责与关系表达，不把位置和连线误当成业务时序。
- 数据交互回答“请求、事件和数据如何传递”，再展开接口、消息、关联标识、字段与存储。

同一张主图保持同一层次。需要多个视角时分图或分页面区域，并说明各自用途，不在业务节点里穿插接口、表字段或消息落库步骤。用户目的是快速回忆项目时，以一张业务主图和少量关键分支为入口，其他视角仅在有助于理解时另行提供；技术细节不因出现在材料里就自动进入产物。

### 2. 找到参与方和真正的触发点

按材料列出业务角色、端、系统、服务及外部依赖。C 端可从用户行为开始；B 端可从运营配置、提交或审批开始；系统链路可从接口调用、事件消费、回调或任务调度开始。只画材料里存在的参与方；纯服务链路不添加虚构的“用户”。

角色与其使用的系统按解释需要拆开或合并；服务内部存储只在方案明确且有助于理解状态时展示。首次出现的简称说明其职责。

### 3. 还原交互和状态

按所选视图说明关键步骤：业务流程保留动作、判断、状态和完成点；模块联动保留职责与依赖；数据交互再说明发起方、接收方、输入输出、关联标识和时间关系。只解释影响本次理解的信息。

- 展开数据交互时，同步调用、返回、事件发送、回调、并行处理、延迟和定时任务采用不同表达；异步入口注明由什么事件继续推进。
- 按真实分支和依赖排序。并行分支的排版顺序不表示业务先后；条件互斥的分支不画成依次执行。
- 数据关联属于本次范围时，解释关键对象如何跨系统关联，区分短期关联信息、长期映射、配置快照和当前状态；实际凭据或客户数据不进入示例。
- 区分操作提交、请求受理、业务完成、下游生效或展示。只有方案明确才能认定这些时点相同；没有完成标准时标为待确认。
- 只展开影响主线理解的生命周期和失败分支，详细操作与技术异常按用户需要另行说明。技术上可能出现但方案未定义的异常作为待确认问题，不直接画入确定路径。

### 4. 用适合的图解释

将主图、必要说明和来源依据整合到一份可离线打开的 HTML。业务流程可用普通流程图或按角色划分的泳道图；服务调用适合时序图；模块关系使用独立关系图或职责表。不要把所有任务都套成服务调用时序图。快速回顾场景优先让读者先看到完整主线，来源和补充说明可折叠查看。

先控制范围，再决定是否拆图。长链路可按阶段拆图，用明确的衔接点保持闭环；不能把超出用户终点的内容拆成多图后继续堆入。每张图说明起点、终点和用途，区分必须步骤、条件分支与独立前提。

需要调用或消息时序泳道图时读取 [流程模型与渲染约定](references/flow-model.md)，将 `flow.json` 放在本次任务的专用临时目录，使用本技能同目录的脚本生成临时 SVG：

```bash
python3 "<技能目录>/scripts/render_flow.py" "<临时目录>/flow.json" -o "<临时目录>/flow.svg"
```

`<技能目录>` 替换为本次加载的 `SKILL.md` 所在目录，`<临时目录>` 替换为本次任务的专用临时目录；不得把某台机器的绝对路径写回技能。用户输入和最终 HTML 的相对路径按用户项目目录解析。

脚本只负责调用时序的渲染和结构校验，无法判断需求事实或范围是否正确。普通业务流程可直接用 SVG、HTML/CSS 或可用的 Mermaid 等工具绘制，无需转换为接口消息。事实性步骤的来源、假设与待确认标记须保留在最终 HTML 的图或说明中，不能只放在待清理的 JSON 里；不能只给一段图源码。

### 5. 检查是否讲清楚

先检查主图是否能直接回答用户的问题、是否止于约定终点，以及是否混入另一个视图的细节。再沿入口核对动作、条件、分支和状态；涉及数据交互时另查关联信息、异步触发点和完成信号，避免把局部成功误当成整条业务完成。

用浏览器或图像工具查看实际图，确认文字和箭头可读、分支含义明确、长标识不被误拆、内容无裁切。检查来源能否定位回原材料，假设和待确认没有混进已确定路径。验证 HTML 的目录、内嵌图和大图查看功能；将 HTML 单独放到临时空目录，断网检查图文和查看功能，确认没有对过程文件的依赖，再清理本轮临时文件。

## 交付与技能协作

- 每次任务只保留一份最终 HTML。流程说明、泳道图、来源依据及待确认问题都放入该文件；配套说明参考 [输出模板](assets/output-template.md)，按需求复杂度裁剪。
- 输出目录遵循用户指定位置；未指定时使用当前 workspace 的交付目录。输入方案和已确认的历史产物保持原样。
- 流程模型 JSON、SVG、说明或组装 Markdown、提取稿、截图及校验副本均为过程文件，统一放在专用临时目录，不在交付目录创建图源文件夹。最终 HTML 验证通过后，自动清理本轮生成的过程文件和临时目录，无需询问。清理范围只包含本轮生成且已整合进 HTML 的文件。
- 需要文档式排版时可使用 `doc-to-html`；适合以主图为中心的页面也可直接生成 HTML。组装稿和图文件均放临时目录，图像、样式、脚本与必要说明全部内嵌，不使用 `--link-images`，不依赖网络或旁置文件，也不保留指向 Markdown、SVG、JSON 等过程文件的链接。
- 用户要求在会话中交互查看时，可补充预览；落盘交付仍只有一份 HTML。本项目的 Markdown 文档及技能模板是维护资源，不复制为业务交付件。
- 用户进一步要求测试设计时再使用 `testcase-bdd-sdd`。流程解读可以作为分析输入，测试技能仍按原始需求核对事实；普通的理解流程或画图请求不自动扩展成测试用例设计。
