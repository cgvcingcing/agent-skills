# 测试用例编写规范

本文档定义测试用例的编写标准，确保用例质量、可读性和可执行性。

---

## 一、用例标题规范

### 格式
```
动作 + 对象 + 条件/场景
```

### 正确示例
- ✅ 系统汇总表展示【系统】标签
- ✅ 用户输入正确账号密码登录成功
- ✅ 订单金额超过 10000 元时提示超限
- ✅ 列表为空时显示空状态提示

### 错误示例
- ❌ 测试登录功能（太模糊）
- ❌ 正常登录（使用了"正常"模糊词）
- ❌ 验证系统表标签显示（标题不应包含"验证"）
- ❌ 检查排序是否正确（标题不应包含"检查""是否"）

### 禁用词汇
- **模糊词**：正常、正确、成功、失败、异常
- **验证词**：验证、检查、确认、测试、校验
- **疑问词**：是否、能否、可否

### 替代方案
- "正常登录" → "使用有效账号密码登录"
- "验证标签显示" → "系统汇总表展示【系统】标签"
- "检查排序是否正确" → "系统表排在自定义表上方"

## 二、优先级判定规范

### 判定标准

| 优先级 | 定义 | 判定依据 | 缺陷影响 |
|-------|------|---------|---------|
| **P0** | 阻塞级 | 主流程无法完成、系统崩溃、数据丢失 | 阻塞发版 |
| **P1** | 高优先级 | 核心功能异常、大量用户受影响 | 必须修复 |
| **P2** | 中优先级 | 次要功能缺陷、部分用户受影响 | 计划修复 |
| **P3** | 低优先级 | 边缘场景、极少用户、UI 优化 | 可接受 |

### 判定流程
```
是否影响主流程？
  ↓ 是 → P0
  ↓ 否
是否影响核心功能？
  ↓ 是 → P1
  ↓ 否
是否影响常用功能？
  ↓ 是 → P2
  ↓ 否 → P3
```

### 示例

| 用例 | 优先级 | 理由 |
|------|--------|------|
| 用户登录 | P0 | 主流程，无法登录则无法使用系统 |
| 系统汇总表展示【系统】标签 | P0 | 核心需求，直接影响用户识别 |
| 列表支持分页 | P1 | 核心功能，影响大数据量展示 |
| 密码错误 5 次锁定 | P1 | 安全功能，重要但不阻塞主流程 |
| 列表支持搜索 | P2 | 常用功能，提升效率 |
| 支持夜间模式 | P3 | 易用性优化，不影响功能 |

## 三、前置条件规范

### 定义
执行测试用例前，系统必须满足的状态或环境。

### 编写原则
- 只写**非显而易见**的前置条件
- 必须**明确具体**
- 可以**独立准备**

### 正确示例
- ✅ 列表中存在 3 个系统汇总表和 2 个自定义汇总表
- ✅ 用户已登录且拥有管理员权限
- ✅ 数据库中订单表有 100 条历史记录

### 错误示例
- ❌ 用户已登录（对于需要登录的功能，这是显而易见的）
- ❌ 系统正常运行（太模糊）
- ❌ 有网络连接（除非特殊说明，这是默认的）

### 何时不写前置条件
- 对所有用例都适用的通用条件（如"系统已启动"）
- 显而易见的条件（如登录页面的"用户未登录"）
- 在操作步骤中已明确准备的条件

## 四、操作步骤规范

### 编写原则
- **每步一个原子操作**（不能再拆分）
- **步骤编号**：从 1 开始连续递增
- **动作明确**：使用"点击"、"输入"、"选择"等明确动词
- **禁止验证动词**：不使用"验证"、"检查"、"确认"

### 格式
```
N. 动作 + 对象 + 具体内容
```

### 正确示例
```
1. 打开汇总表列表页面
2. 定位到第一个系统汇总表
3. 查看标签展示区域
```

### 错误示例
```
❌ 1. 打开页面并查看列表（合并了两个动作）
❌ 2. 验证系统表有标签（使用了"验证"）
❌ 3. 检查排序是否正确（使用了"检查"）
❌ 4. 确认显示正常（使用了"确认"和"正常"）
```

### 拆分规则

**错误**（多动作合并）：
```
1. 输入用户名和密码并点击登录
```

**正确**（拆分为原子操作）：
```
1. 在用户名输入框输入"test@example.com"
2. 在密码输入框输入"Test@123"
3. 点击"登录"按钮
```

### 特殊场景处理

**场景 1：等待/观察**
```
1. 点击"提交"按钮
2. 等待页面加载完成
3. 查看页面内容
```

**场景 2：多个验证点在同一步骤**
- 操作步骤只写操作，验证点放在预期结果中

## 五、预期结果规范

### 编写原则
- **编号与操作步骤对应**（1 对 1）
- **具体可验证**（包含具体数据/状态）
- **一个步骤的多个验证点用逗号连接**，写在同一条预期结果中

### 格式
```
N. 具体的可观察结果
```

### 正确示例
```
操作步骤：
1. 打开汇总表列表页面
2. 查看系统汇总表的标签
3. 查看自定义汇总表的标签

预期结果：
1. 页面正常加载，显示所有汇总表
2. 系统汇总表展示【系统】标签，标签颜色为蓝色，位置在表名右侧
3. 自定义汇总表不展示【系统】标签
```

### 错误示例
```
❌ 1. 系统正常处理（太模糊）
❌ 2. 正常显示（没有具体内容）
❌ 3. 功能正常（无法验证）
❌ 4. 符合需求（过于抽象）
```

### 多验证点处理

**场景：一个操作有多个验证点**

**错误**（拆分成多条预期结果）：
```
操作步骤：
1. 点击"提交"按钮

预期结果：
1a. 按钮变为禁用状态
1b. 显示 loading 图标
1c. 提交成功提示
```

**正确**（用逗号连接在同一条）：
```
操作步骤：
1. 点击"提交"按钮

预期结果：
1. 按钮变为禁用状态，显示 loading 图标，提交成功后显示"提交成功"提示
```

### 数量对应规则
- 步骤数组长度 = 预期结果数组长度
- 步骤编号 = 预期结果编号

## 六、标签规范

### 用途
- 标识适用端（PC / APP / 小程序）
- 标识功能模块
- 标识测试类型

### 格式
```
标签1, 标签2, 标签3
```

### 常用标签

**适用端**：
- PC
- APP
- 小程序
- C端（PC + APP）
- B端

**功能模块**：
- 列表
- 新增
- 编辑
- 删除
- 导入
- 导出
- 详情
- 权限

**测试类型**：
- 接口
- UI
- 性能
- 安全
- 兼容性

### 示例
```json
{
  "标签": "PC, 列表, 接口"
}
```

## 八、质量检查清单

### 用例完整性检查
- [ ] 用例 ID 唯一
- [ ] 标题符合规范（无模糊词）
- [ ] 优先级已标注
- [ ] 测试点 ID 已关联
- [ ] 需求 ID 已关联
- [ ] 设计方法已标记

### 步骤质量检查
- [ ] 每步一个原子操作
- [ ] 步骤编号连续
- [ ] 步骤无验证动词
- [ ] 预期结果编号与步骤对应
- [ ] 预期结果具体可验证

### 可执行性检查
- [ ] 前置条件明确可准备
- [ ] 操作步骤明确可执行
- [ ] 预期结果明确可验证
- [ ] 无逻辑矛盾
