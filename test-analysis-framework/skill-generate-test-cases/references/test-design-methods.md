# 18 种测试设计方法详解

本文档详细说明每种测试设计方法的定义、应用场景、实施步骤和示例。

---

## 一、经典黑盒方法（8 种）

### 1. 等价类划分法（Equivalence Partitioning, EP）

#### 定义
将输入数据划分为若干等价类，同一等价类中的数据对程序的影响是等价的。

#### 适用场景
- 有明确的输入范围、格式要求
- 输入值为枚举类型
- 输入有有效/无效之分

#### 实施步骤
1. 识别输入条件
2. 划分有效等价类和无效等价类
3. 为每个等价类设计测试用例
4. 有效类可合并测试，无效类必须单独测试

#### 示例
**需求**：用户名长度 3-20 位，支持字母和数字

**等价类划分**：
- 有效类：3-20 位字母数字组合
- 无效类 1：< 3 位
- 无效类 2：> 20 位
- 无效类 3：包含特殊字符
- 无效类 4：空值

**生成用例**：
- TC-001：输入 10 位字母数字（有效类）
- TC-002：输入 2 位字符（无效类 1）
- TC-003：输入 21 位字符（无效类 2）
- TC-004：输入特殊字符 @#$（无效类 3）
- TC-005：输入空值（无效类 4）

---

### 2. 边界值分析法（Boundary Value Analysis, BVA）

#### 定义
对输入输出的边界值进行测试，因为大量缺陷发生在边界附近。

#### 适用场景
- 有数值范围限制
- 有长度限制
- 有时间范围

#### 实施步骤
1. 识别边界条件
2. 确定上点、离点、内点
3. 为每个边界设计测试用例

#### 边界点定义
- **上点（On Point）**：边界值本身
- **离点（Off Point）**：边界外侧最近的点
- **内点（In Point）**：边界内侧的任意点

#### 示例
**需求**：订单金额 1-10000 元

**边界值**：
- 下边界 -1：0 元（离点）
- 下边界：1 元（上点）
- 内点：5000 元
- 上边界：10000 元（上点）
- 上边界 +1：10001 元（离点）

**生成用例**：
- TC-001：输入 0 元（期望：提示金额过低）
- TC-002：输入 1 元（期望：通过）
- TC-003：输入 5000 元（期望：通过）
- TC-004：输入 10000 元（期望：通过）
- TC-005：输入 10001 元（期望：提示金额超限）

---

### 3. 判定表法（Decision Table, DT）

#### 定义
用表格形式表示多个条件组合与对应动作的关系。

#### 适用场景
- 多个条件共同决定一个结果
- 业务规则复杂，条件组合多

#### 实施步骤
1. 列出所有条件
2. 列出所有可能的动作
3. 列举所有条件组合
4. 确定每种组合对应的动作
5. 简化判定表（合并相同动作的组合）
6. 为每列生成一个测试用例

#### 示例
**需求**：会员折扣规则
- 条件 1：会员等级（VIP/普通）
- 条件 2：订单金额（>500 / ≤500）
- 条件 3：首单优惠（是/否）
- 动作：折扣率

**判定表**：

| 规则 | R1 | R2 | R3 | R4 | R5 | R6 | R7 | R8 |
|------|----|----|----|----|----|----|----|----|
| VIP | Y | Y | Y | Y | N | N | N | N |
| >500 | Y | Y | N | N | Y | Y | N | N |
| 首单 | Y | N | Y | N | Y | N | Y | N |
| **折扣** | **0.8** | **0.85** | **0.9** | **0.9** | **0.9** | **0.95** | **0.95** | **1.0** |

**生成用例**：为每列生成 1 个测试用例（共 8 个）

---

### 4. 因果图法（Cause-Effect Graphing, CEG）

#### 定义
分析输入条件（原因）与输出结果（结果）之间的因果关系，用图形表示。

#### 适用场景
- 输入条件之间有约束关系
- 输入组合复杂
- 需要找出最少的测试用例覆盖所有组合

#### 实施步骤
1. 分析需求，识别原因（输入）和结果（输出）
2. 分析原因之间的关系（与、或、非）
3. 绘制因果图
4. 将因果图转换为判定表
5. 为判定表的每列生成测试用例

#### 示例
**需求**：文件打开功能
- 原因 1：文件存在
- 原因 2：文件可读
- 结果：打开成功 / 提示文件不存在 / 提示无权限

**因果关系**：
- 文件存在 AND 文件可读 → 打开成功
- NOT 文件存在 → 提示文件不存在
- 文件存在 AND NOT 文件可读 → 提示无权限

---

### 5. 状态迁移法（State Transition Testing, STT）

#### 定义
测试系统在不同状态之间的转换是否正确。

#### 适用场景
- 对象有明确的生命周期
- 存在状态转换
- 工作流、审批流

#### 实施步骤
1. 识别所有状态
2. 识别状态转换事件
3. 绘制状态转换图
4. 为每个转换生成测试用例
5. 覆盖无效转换（不允许的状态跳转）

#### 示例
**需求**：订单状态流转
- 状态：待支付 → 已支付 → 已发货 → 已收货

**状态转换表**：

| 当前状态 | 事件 | 下一状态 |
|---------|------|---------|
| 待支付 | 支付成功 | 已支付 |
| 待支付 | 超时/取消 | 已取消 |
| 已支付 | 商家发货 | 已发货 |
| 已发货 | 用户确认收货 | 已收货 |
| 已发货 | 用户申请退货 | 退货中 |

**生成用例**：
- TC-001：待支付 → 支付 → 已支付
- TC-002：待支付 → 取消 → 已取消
- TC-003：已支付 → 发货 → 已发货
- TC-004：已发货 → 确认 → 已收货
- TC-005：无效转换：待支付 → 直接已发货（期望：拒绝）

---

### 6. 场景法（Scenario Testing, ST）

#### 定义
模拟用户实际使用场景，测试端到端的业务流程。

#### 适用场景
- 多步骤业务流程
- 用户故事
- 端到端测试

#### 实施步骤
1. 识别基本流（主成功场景）
2. 识别备选流（可接受的替代路径）
3. 识别异常流（错误处理）
4. 为每个流生成测试用例

#### 示例
**需求**：用户登录

**基本流**：
1. 打开登录页
2. 输入账号密码
3. 点击登录
4. 跳转首页

**备选流**：
- 备选流 1：记住密码
- 备选流 2：验证码登录

**异常流**：
- 异常流 1：密码错误
- 异常流 2：账号不存在
- 异常流 3：网络超时

**生成用例**：
- TC-001：基本流（正常登录）
- TC-002：基本流 + 记住密码
- TC-003：验证码登录
- TC-004：密码错误提示
- TC-005：账号不存在提示
- TC-006：网络超时重试

---

### 7. 正交试验法（Orthogonal Array Testing, OAT）

#### 定义
用最少的测试用例覆盖多因素、多水平的参数组合。

#### 适用场景
- 配置项测试
- 参数组合测试
- 兼容性测试

#### 实施步骤
1. 确定因素（变量）和水平（取值）
2. 选择合适的正交表
3. 根据正交表生成测试用例

#### 示例
**需求**：搜索功能配置测试
- 因素 1：搜索类型（商品/店铺/品牌）- 3 水平
- 因素 2：排序方式（价格/销量/评分）- 3 水平
- 因素 3：筛选条件（有/无）- 2 水平
- 因素 4：分页大小（10/20/50）- 3 水平

全组合需要：3 × 3 × 2 × 3 = 54 个用例

使用 L9(3^4) 正交表，只需 **9 个用例**即可覆盖主要组合。

---

### 8. 错误推测法（Error Guessing, EG）

#### 定义
基于经验和直觉，推测程序可能存在的缺陷。

#### 适用场景
- 经验丰富的测试人员
- 高风险模块
- 历史缺陷多的区域

#### 常见错误模式
- 空值、null、undefined
- 特殊字符：`' " < > & \ / # @ !`
- 极端值：0、-1、MAX_INT
- 重复提交、并发操作
- 网络异常、超时
- XSS、SQL 注入

#### 示例
**需求**：用户名输入

**错误推测用例**：
- TC-001：输入 SQL 注入字符串 `' OR '1'='1`
- TC-002：输入 XSS 脚本 `<script>alert(1)</script>`
- TC-003：输入超长字符串（1000 字符）
- TC-004：输入 emoji 表情
- TC-005：快速连续提交（防重复提交）

## 二、扩展方法（10 种）

### 9. 用例组合法（Pairwise Testing）

#### 定义
两两参数组合覆盖，减少全组合的用例数量。

#### 适用场景
- 多个独立参数
- 参数之间交互影响小
- 配置测试、兼容性测试

#### 示例
**需求**：配置项测试
- 浏览器：Chrome / Firefox / Safari
- 操作系统：Windows / Mac / Linux
- 分辨率：1920x1080 / 1366x768

全组合：3 × 3 × 2 = 18 个

Pairwise：至少需要 **9 个用例**覆盖浏览器与操作系统的全部 9 种组合；最终数量必须按生成的组合表验证，不能只根据经验估算

---

### 10. 流程分析法（Flow Analysis）

#### 定义
分析业务流程的各个分支路径，确保每条路径都被测试。

#### 适用场景
- 复杂业务流程
- 多分支、多决策点

---

### 11. 分类树法（Classification Tree Method, CTM）

#### 定义
将输入分类为树形结构，系统性地组合测试。

---

### 12. 探索性测试法（Exploratory Testing）

#### 定义
测试设计和测试执行同时进行，边测边学习。

#### 适用场景
- 需求不明确
- 新功能探索
- 补充脚本化测试

---

### 13. 基于风险的测试（Risk-Based Testing, RBT）

#### 定义
根据风险优先级分配测试资源。

#### 风险评估
- 影响度：高/中/低
- 发生概率：高/中/低
- 风险等级 = 影响度 × 发生概率

---

### 14. 基于模型的测试（Model-Based Testing, MBT）

#### 定义
从形式化模型自动生成测试用例。

---

### 15. 接口测试设计（API Testing Design）

#### 核心测试点
- 参数校验（必填、类型、格式、范围）
- 返回结果验证（状态码、数据结构、业务字段）
- 异常处理（参数缺失、类型错误、权限不足）
- 性能测试（响应时间、并发）

---

### 16. 性能测试设计（Performance Testing Design）

#### 核心场景
- 负载测试：逐步增加负载
- 压力测试：超出最大负载
- 稳定性测试：长时间运行
- 并发测试：多用户同时操作

---

### 17. 安全测试设计（Security Testing Design）

#### 核心测试点
- 权限控制：垂直越权、水平越权
- 注入攻击：SQL 注入、XSS、CSRF
- 数据加密：密码、敏感信息
- 会话管理：token 过期、并发登录

---

### 18. 兼容性测试设计（Compatibility Testing Design）

#### 测试维度
- 浏览器：Chrome / Firefox / Safari / Edge
- 操作系统：Windows / Mac / Linux / iOS / Android
- 分辨率：1920x1080 / 1366x768 / 移动端各尺寸
- 设备：PC / 手机 / 平板

---

## 三、方法选择决策树

```
需求特征
  ├─ 有输入范围/格式？ → EP + BVA
  ├─ 多条件组合决定结果？ → DT
  ├─ 有状态流转？ → STT
  ├─ 多步骤流程？ → ST
  ├─ 大量参数组合？ → OAT / Pairwise
  ├─ 接口测试？ → API Testing Design
  ├─ 性能需求？ → Performance Testing Design
  ├─ 安全需求？ → Security Testing Design
  └─ 高风险？ → EG + RBT
```

## 四、方法组合策略

### 常见组合

| 场景类型 | 推荐方法组合 |
|---------|-------------|
| 表单输入 | EP + BVA + EG |
| 业务流程 | ST + STT + EG |
| 复杂规则 | DT + CEG + EP |
| 接口测试 | API Design + EP + BVA |
| 配置测试 | OAT + Pairwise |
