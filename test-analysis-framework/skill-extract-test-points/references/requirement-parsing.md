# 需求解析规则

本文档定义如何从需求文档中提取信息，区分事实和推断。

---

## 核心原则

### 1. 不编造原则
- ✅ 只提取需求文档中**明确存在**的信息
- ❌ 不凭空编造需求中不存在的概念、术语、规则
- ⚠️ 不清楚的地方必须标记为"待确认"

### 2. 事实与推断分离
所有提取的信息必须标注类型：
- **F (Fact)**: 事实 - 从需求文档中直接获取的信息
- **I (Inference)**: 推断 - 基于事实进行的合理推断

### 3. 可追溯原则
每条信息必须能追溯到需求文档的具体位置。

---

## 信息分类标准

### Fact (事实) - F
**定义**：需求文档中明确写出的内容，可以直接引用原文。

**判断标准**：
- 文档中有明确的文字描述
- 图片中清晰可见的文字
- 表格、列表中的具体数据
- 明确标注的配置项、字段名

**示例**：
- ✅ "新人三单楼层配置"（文档中明确的功能名称）
- ✅ "生效平台：App、小程序"（明确列出的平台）
- ✅ "已下单 #1 ~ #3 单"（明确的订单数量范围）

### Inference (推断) - I
**定义**：基于事实进行的合理推断，用于补充理解，但非文档明确说明。

**判断标准**：
- 基于多条事实的逻辑推导
- 基于业务常识的补充
- 基于技术实现的推测
- 基于用户场景的扩展

**示例**：
- 🔶 "后台需要新增配置接口"（基于"后台配置"推断）
- 🔶 "需要判断用户是否领取了优惠券"（基于"有优惠券才展示"推断）
- 🔶 "需要查询订单状态"（基于"判断订单状态"推断）

---

## 信息提取流程

### Phase 1: 直接提取（Fact）
1. 逐句阅读需求文档
2. 提取明确的功能名称、字段、规则
3. 记录原文位置（段落、截图区域）

**输出格式**：
```json
{
  "type": "F",
  "content": "新人三单楼层配置",
  "source": "需求标题",
  "confidence": "high"
}
```

### Phase 2: 合理推断（Inference）
1. 基于已提取的事实
2. 进行业务逻辑推断
3. 标注推断依据

**输出格式**：
```json
{
  "type": "I",
  "content": "需要新增后台配置接口",
  "based_on": ["F: 后台配置模块", "F: 配置生效平台"],
  "confidence": "medium"
}
```

### Phase 3: 识别冲突和歧义
1. 检查事实之间的矛盾
2. 识别规则冲突
3. 标记为"待确认"

**输出格式**：
```json
{
  "type": "conflict",
  "description": "规则冲突：条件A 与条件B 矛盾",
  "facts": ["F1", "F2"],
  "need_clarification": true
}
```

## 意图串联与流程分析

### 定义
基于提取的事实和推断，分析完整的业务流程和状态生命周期。

### 分析维度

#### 1. 状态生命周期
识别对象的完整生命周期，包括：
- 初始状态
- 中间状态
- 终止状态
- 状态转换条件

**示例**：
```
新人三单楼层的生命周期：
- 初始：用户未下单
- 触发：用户下单第1单且未取消
- 展示：楼层开始展示，显示对应文案
- 进行中：第2单、第3单时更新文案
- 结束：完成第3单或取消任一订单
```

#### 2. 规则约束关系
分析多条规则之间的关系：
- 前置条件 → 触发条件
- 必要条件 vs 充分条件
- 规则优先级

**示例**：
```
展示条件分析：
前置条件：用户已下单 #1 ~ #3 单（F）
必要条件：有系统发放的新人三单优惠券（F）
触发条件：第1单且未取消订单（F）

关系：触发条件是展示的开始节点，但整个展示周期内需要持续满足前置条件和必要条件
```

#### 3. 业务流程串联
将碎片化的规则串联成完整的业务流程：

**示例**：
```
完整流程：
1. 用户注册/登录
2. 系统发放新人三单优惠券
3. 用户下单第1单
4. 判断订单状态（未取消）
5. 展示新人三单楼层（显示首单文案）
6. 用户下单第2单
7. 更新文案为次单文案
8. 用户下单第3单
9. 更新文案为三单文案
10. 第3单完成后楼层消失
```

#### 4. 识别规则冲突
发现文档中的矛盾或不清晰之处：

**识别方法**：
- 同一条件出现多次，但描述不一致
- 规则之间互相矛盾
- 时序逻辑不清晰

**处理方式**：
- 标记为"规则冲突"
- 给出合理解释（推断）
- 列入"待确认问题"

```json

  "title": "用户下单第1单且未取消时展示新人三单楼层",
  "description": "...",
  ...
}
```

**新增字段**：
```json
{
  "id": "TP-001",
  "title": "用户下单第1单且未取消时展示新人三单楼层",

  "source_facts": ["用户下单第一单且未取消", "需要判断订单状态"],
  "confidence": "high",  // high/medium/low
  "lifecycle_stage": "trigger",  // 生命周期阶段
  "rule_type": "trigger_condition",  // 规则类型
  "description": "...",
  ...
}
```

```markdown
## 4. 意图串联与流程分析

### 4.1 状态生命周期

新人三单楼层的完整生命周期：

\`\`\`mermaid
stateDiagram-v2
    [*] --> 未展示: 用户注册
    未展示 --> 首单展示: 下单第1单且未取消
    首单展示 --> 次单展示: 下单第2单且未取消
    次单展示 --> 三单展示: 下单第3单且未取消
    三单展示 --> [*]: 第3单完成
    
    首单展示 --> 取消: 取消订单
    次单展示 --> 取消: 取消订单
    三单展示 --> 取消: 取消订单
    取消 --> [*]
\`\`\`

### 4.2 规则冲突分析

**冲突点 1**：展示条件的时序矛盾

- **事实 F4**：需要满足"已下单#1~#3单 且有优惠券"
- **事实 F6**：在"下单第1单且未取消"时就开始展示

**冲突分析**：
- F4 表述的是整个展示周期的适用对象（#1~#3单的用户）
- F6 表述的是展示的触发时机（第1单完成时）

**合理解释（推断）**：
1. 楼层展示的**开始节点**是第1单且未取消
2. 楼层展示的**持续条件**是用户处于#1~#3单阶段且有优惠券
3. 楼层根据当前订单数（第1/2/3单）回显不同的文案

### 4.3 完整业务流程

\`\`\`
1. [前置] 用户注册/登录
2. [前置] 系统发放新人三单优惠券（首单、次单、三单各一张）
3. [触发] 用户下单第1单
4. [判断] 订单状态是否为"已取消"？
   - 是 → 楼层不展示
   - 否 → 继续
5. [展示] 首页展示"新人三单楼层"，显示"首单文案"
6. [进行] 用户下单第2单
7. [更新] 楼层文案更新为"次单文案"
8. [进行] 用户下单第3单
9. [更新] 楼层文案更新为"三单文案"
10. [结束] 第3单完成后，楼层消失
\`\`\`
```
